# 01.13.0 — AP Architecture Audit & XCOM Action Economy Study

**Status:** Research and design proposal. No 01.13 gameplay behavior is implemented by this document.
**Audit baseline:** `p2-foundation` at `2f43e0c` (`document the three second beat`)
**Local XCOM evidence:** XCOM 2: War of the Chosen SDK under `C:\Program Files (x86)\Steam\steamapps\common\XCOM 2 War of the Chosen SDK`

## 1. Executive summary

FuseFire already has one authoritative runtime owner for AP: `UnitStats`. Actions query and validate that state through `TacticalActionService`, commit AP changes synchronously, and expose the committed value to turn progression, AI, HUD, replay results, and fingerprints. A new AP manager would duplicate authority and is not justified.

The current `max_ap` field combines two future concepts: configured base AP and effective maximum AP. `current_ap` is sufficient while the maximum is static, but it cannot express the approved mid-activation rules by itself. In particular, lowering a maximum after AP has been spent must account for expenditure, while removing that penalty must not restore AP during the same activation.

The smallest viable extension is:

1. rename the configured concept to `base_ap` in the archetype/stat boundary;
2. derive `effective_max_ap` from base AP plus a small AP-only modifier collection;
3. retain an activation-local capacity ceiling and spent-AP count;
4. derive ordinary available AP from those activation values;
5. keep explicit current-AP grants separate if and when a real grant mechanic is approved.

The activation capacity ceiling is the key addition. It is set from the effective maximum at activation refresh and may ratchet downward during that activation. It does not rise again until the next refresh. This satisfies maximum reduction, same-activation modifier removal, and modifier expiration without inventing refunds.

Movement range is already independent. One Move costs 1 AP, while `UnitStats.speed` is a weighted path budget. FuseFire should preserve that separation and should consider renaming `speed` to `movement_range` in a later, compatibility-conscious slice only if the clarity gain justifies the migration.

The local WOTC SDK confirms several useful principles: action points are authoritative unit state, ability costs validate and consume them, actions may consume one point or all remaining points, bonus points are granted explicitly, and Mobility controls travel distance separately. FuseFire should adopt those boundaries without copying XCOM's typed action-point token system or its two-action balance.

## 2. Current AP architecture map

### 2.1 Configuration and initialization

`units/components/unit_stats.gd` owns runtime AP:

- `@export_range(1, 20, 1) var max_ap: int = 2` is the scene fallback and clamps to at least 1.
- `var current_ap: int = 2` clamps to `0...max_ap` and emits `ap_changed(current, max_ap)`.
- `_ready()` initializes `current_ap = max_ap`.
- `reset_ap()` restores `current_ap = max_ap`.
- `has_enough_ap()` and `consume_ap()` are the common query/mutation helpers.

`units/archetypes/tactical_archetype.gd` is the authored unit-configuration boundary. Its Inspector-editable `max_ap` override uses `0` as “keep the scene fallback.” `apply_starting_configuration()` writes both `unit.stats.max_ap` and `current_ap`. All current MIRA Resources under `units/archetypes/` explicitly set 3 AP. `tests/tactical_archetype_lab_test.gd` verifies both the authored value and spawned runtime value.

This is already data-driven and has no class-name or species-name check. The archetype Resource is the correct home for future `base_ap`.

### 2.2 Refresh and activation lifecycle

`systems/turn_manager.gd` refreshes every living roster member in a faction when that faction phase begins:

- `_start_player_turn_phase()` calls `reset_turn()` for player units;
- `_start_ally_turn_phase()` does the same for allied units;
- `_start_enemy_turn_phase()` does the same for enemy units.

`UnitStats.reset_turn()` resets AP and legacy Defend state. Tactical states use a separate `TacticalState.begin_activation()` call in `TurnManager._set_active_unit()`.

This means AP refresh is currently a **phase-start operation**, not a shared beat-boundary operation and not strictly a per-unit callback. It works because each faction receives one phase per round and all of its units are prepared together. The implementation should preserve visible behavior while 01.13 introduces an explicit activation refresh API.

### 2.3 Query, validation, commit, and presentation

`systems/actions/runtime/tactical_action_service.gd` is the authoritative action gateway:

1. query methods capture `actor_ap_before`, predicted `actor_ap_after`, and an `ActionCost`;
2. `_validate_actor()` rejects missing, defeated, inactive, moving, or insufficient-AP actors;
3. submit methods re-query against the request revision;
4. commits call `consume_ap()` or explicitly set AP to zero;
5. results capture committed before/after values;
6. presentation receives the immutable committed result.

`systems/actions/runtime/action_cost.gd` already expresses the needed cost categories: fixed `ap`, `spend_all_remaining_ap`, `ends_activation`, and `requires_active_actor`. It should remain the action-cost contract. It should not become an AP state owner.

AP mutations are mostly centralized through `consume_ap()`. Guard and Wait directly set `current_ap = 0` because they end the activation. Those direct assignments are coherent today but should become a named `spend_all_remaining_ap()` operation when spent AP becomes explicit.

### 2.4 Exhaustion, selection, zero AP, and defeat

For player units, `TurnManager` connects `ap_changed`. A transition to zero schedules `_advance_selection_if_needed()` after the action barrier and movement finish. The manager selects another living player with `current_ap > 0`, or emits `player_actions_exhausted`.

Zero AP is not identical to “nothing legal remains.” The existing exception is `zero_ap_continuation_available`, provided by `BattleController` for a free terminal interaction. After a free objective action, `complete_free_objective_action()` rechecks the exhausted unit and resumes selection progression.

AI controllers loop while `current_ap > 0`. Wait and Guard set AP to zero, and automated player/faction queues advance. `TurnManager.advance_automated_player()` also guards against an AP signal having already selected the next actor.

Defeat flows from `UnitStats.take_damage()` to `TacticalUnit`, `BattleController`, and `TurnManager.remove_unit()`. If the defeated unit was active, continuation waits for the presentation barrier, selects another eligible unit or advances the phase, and checks battle outcome. Nested reaction damage and beat damage use this same path.

The current zero-AP terminal exception is deliberately narrow. Rescue, extraction, and terminal actions all have `ActionCost(0)` and require an active, living, authorized actor. Rescue and extraction may also occur as mission consequences, but UI-driven terminal use is the present zero-AP continuation case.

### 2.5 Ability interaction table

| Mechanic | Current AP behavior | 01.13 implication |
| --- | --- | --- |
| Move | Fixed 1 AP; range comes from `stats.speed`. | Query effective current AP; leave range independent. |
| Attack | Fixed 1 AP and 1 SP when enabled. | No cost change. |
| Reload | Fixed 1 AP. | No cost change; exact-one-AP AI branches need 0–4 AP coverage. |
| Aim | Fixed 1 AP; Jammed rejects it. | No cost change. |
| Defend | Legacy fixed 1 AP simple action. | Preserve replay/tests; do not restore as new design. |
| Shield Stance | Capability-authored AP cost, currently 1. | Validate against current AP; stance restrictions remain separate. |
| Guard | Requires at least 1 AP, records all remaining as cost, sets current AP to 0, ends activation. | Use named spend-all commit; modifiers change what “remaining” means, not reaction count. |
| Emergency Seal | Fixed 1 AP. | No cost change. |
| Rescue / Extract / Terminal | 0 AP authoritative mission actions. | Must remain legal at 0 AP when activation eligibility permits. |
| Wait / Skip | Consumes all remaining AP and ends activation. | Use named spend-all commit. |
| AI actions | Use the same queries/submissions as player actions. | AI must never calculate a separate effective maximum. |
| Guard reactions | Nested in Move/Attack; watcher spends 1 SP, no AP. | Reaction capability remains independent of AP capacity and movement range. |

No inspected action assumes a universal maximum of exactly 2. Some tests and AI heuristics assume particular **current** values, especially 1, and therefore require broader tempo fixtures.

### 2.6 HUD, portraits, tests, and replay

`ui/action_hud_controller.gd` queries action legality and uses `current_ap >= 1` for Move availability. `ui/unit_portrait.gd`, the AP HUD, and world bars subscribe to `ap_changed` and render current/maximum AP. Portrait exhaustion currently means `current_ap <= 0`.

The action result classes serialize AP before/after for replay verification. `BattleReplayRecording` reconstructs units from archetype IDs and feature flags. `BattleStateFingerprint.capture()` includes `current_ap` for every supported historical fingerprint shape, but it does not include `max_ap`, movement range, an activation ceiling, spent AP, or modifier sources.

Historical compatibility is handled with replay envelope version 3, legacy envelope 2, per-action payload schemas, and feature gates such as conditions. An AI-policy or internal state refactor does not automatically require a payload-schema bump. A new fingerprint shape does require an explicit feature/version gate so old recordings keep their old expected strings.

Representative AP coverage exists in:

- `tests/tactical_archetype_lab_test.gd` — authored 3-AP MIRA configuration;
- `tests/battle_smoke.gd` — three consecutive one-AP actions and next-round refresh;
- `tests/tactical_action_service_test.gd` — query purity, commit cost, duplicate rejection, Wait;
- `tests/overwatch_reactions_test.gd` — Guard spends all AP and reactions spend SP;
- `tests/mission_terminal_interaction_test.gd` and `tests/ai_abilities_integration_test.gd` — free terminal use, including zero AP;
- `tests/tactical_conditions_test.gd` — Emergency Seal AP cost and beat casualties;
- replay suites — result and fingerprint verification across historical feature gates.

## 3. Current movement-range architecture map

### 3.1 Authoritative properties

`UnitStats.speed` is the authoritative number of weighted grid-cost units available to one Move action. It is Inspector-editable with a default of 5. `TacticalArchetype.movement_range` may override it. `TacticalUnit.movement_speed` is a separate presentation value measured in world metres per second.

The current name `speed` is less precise than its actual meaning, but the code comments correctly distinguish it from animation speed. Carrying a rescued unit temporarily subtracts 2 from `stats.speed` and restores the prior value when the carried state ends. No condition currently modifies it.

### 3.2 Path cost and validation

`systems/grid/pathfinder.gd` uses an `AStar3D` graph plus a deterministic Dijkstra reachability query:

- cardinal and ordinary elevation-connected steps cost 1;
- a legal same-level diagonal costs `sqrt(2)`;
- destination-cell `movement_cost` multiplies the step cost;
- generated/authored traversal links are graph edges and retain a one-step base cost;
- diagonal edges exist only when all four cells in the square are clear and stoppable;
- elevation legality is controlled by graph connectivity and `max_step_levels` or authored traversal links;
- only stoppable cells are returned as destinations, though non-stoppable cells may be traversed.

`BattleController._query_move_data()` passes `unit.stats.speed` to `get_reachable_cells()`, validates occupancy, obtains the authoritative path, and returns the exact path cost. `TacticalActionService.query_move()` records the movement budget and path evidence. AI calls the same move query for legal destinations and uses `Pathfinder.get_path_cost()` when scoring routes.

Movement range is therefore neither AP nor a simple count of tiles. It is a weighted path budget. Replay records the resolved path and movement result; the originating movement stat is reconstructed through the archetype/scene rather than fingerprinted directly.

### 3.3 Future movement impairment

The existing stat boundary can support an independent movement modifier later, but direct mutations such as the carry penalty show why a general stat framework is unnecessary for 01.13. A future damaged-actuator mechanic can receive its own small movement-range calculation when it is approved. AP modifiers should not be reused for movement.

## 4. Tactical beat and condition lifecycle

`TurnManager._end_round()` emits synchronous `tactical_beat_ended(current_round)`, checks whether the battle ended, increments the round, emits `round_started`, and begins the next player phase.

`TacticalActionService._on_tactical_beat_ended()` processes registered actors in stable tactical-ID order. `ConditionComponent.tick()` skips conditions applied in the current beat, produces periodic damage/expiration events, and decrements remaining duration. Periodic damage uses `UnitStats.take_damage()`, so defeat follows the normal authoritative removal and outcome path. Conditions do not tick or expire mid-activation.

The implemented boundary order is:

1. enemy phase finishes;
2. `tactical_beat_ended(old_round)` fires;
3. conditions tick and may defeat actors;
4. battle outcome is checked;
5. if ongoing, the round number increments;
6. the new player phase refreshes all player AP;
7. later in that same round, ally and enemy phase starts refresh their respective rosters.

AP refresh and condition processing are adjacent for players but are not the same operation. Allies and enemies refresh only when their phase starts. This is deterministic and should remain observable behavior.

### Recommended ordering for 01.13

Keep condition timing unchanged:

1. finish the old tactical beat and process conditions;
2. resolve casualties and battle completion;
3. begin the new round;
4. refresh an actor's AP capacity when that actor becomes eligible for its new activation/phase;
5. apply no automatic mid-activation AP grant when a modifier expires.

This ordering prevents a unit killed by beat damage from receiving a meaningless refreshed budget and avoids moving 01.12 timing into action code. The fictional beat remains an approximately three-second shared interval; sequential activations remain presentation and decision abstractions.

## 5. XCOM action-economy study

### 5.1 Enemy Unknown / Enemy Within

The official *XCOM: Enemy Within* PC manual states that soldiers normally receive two moves per turn, shows a second movement band for Dashing, says Dashing expends all available movement points, and warns that most actions end the unit's turn even if movement remains. It identifies Run and Gun as an exception that permits moving and firing.

This establishes the player-facing EU/EW principles relevant here:

- a small standard action budget;
- movement range displayed separately from action choice;
- a long movement can consume the remaining turn;
- many attacks/abilities are turn-ending rather than merely priced as one interchangeable action;
- exceptions are explicit abilities.

Evidence: [official XCOM: Enemy Within PC manual](https://assets.2k.com/1a6ngf98576c/7Fciwy21uFjctd6au48k4U/8161612b55a81ecc9461a8a815f55af3/XCOM_EW_PC_MANUAL_ENG.pdf) and [official XCOM: Enemy Unknown PC manual](https://cdn.akamai.steamstatic.com/steam/apps/200510/manuals/XCOM_EU_PC_MANUAL_ENG.pdf?t=1447366133).

The accessible manuals describe rules, not engine ownership or AI implementation. Claims about internal EU/EW data structures remain unverified.

### 5.3 Applicable lessons and deliberate differences

| Lesson | FuseFire decision |
| --- | --- |
| Unit state owns the action budget. | Apply. Keep ownership in `UnitStats`. |
| Ability definitions describe costs; authoritative resolution consumes them. | Apply through `ActionCost` and `TacticalActionService`. |
| Mobility and action economy are separate. | Apply; keep `stats.speed` independent. |
| Turn-ending and consume-all behavior are explicit. | Apply; Guard and Wait already express this. |
| Bonus actions are explicit grants, not maximum changes. | Apply as a future separate API. |
| Named point types enable many special exceptions. | Do not copy now. FuseFire has no approved mechanic requiring typed AP. |
| Standard budget is 2. | Do not copy. FuseFire's MIRA identity currently uses 3; future humans use 2. |
| Dashing can consume a second movement action in one path. | Do not copy. FuseFire deliberately makes one Move cost 1 AP and bounds distance with one movement-range budget. |
| Damage may clear conventional Overwatch reserves. | Do not copy automatically. Good Guard has its own approved tactical-state rules. |

## 6. Proposed FuseFire AP state model

### 6.1 Authoritative fields

Extend `UnitStats`; do not add an AP manager.

| Field/concept | Ownership | Rule |
| --- | --- | --- |
| `base_ap` | Inspector-authored through `TacticalArchetype`, copied into `UnitStats` | Normal capacity before modifiers. Typical MIRA 3, future human 2, exceptional units may use 4. No class-name checks. |
| AP modifiers | `UnitStats`, keyed by stable source ID | Small integer deltas supplied/removed by their owning systems. Sorted snapshots for replay/fingerprints. |
| `effective_max_ap` | Derived read-only value in `UnitStats` | `max(0, base_ap + sum(modifiers))`. |
| `activation_capacity_ap` | Runtime `UnitStats` state | Set to effective maximum on refresh. During an activation it can only stay equal or decrease automatically. |
| `spent_ap` | Runtime `UnitStats` state | Monotonic within an activation; reset to 0 on refresh. |
| `current_ap` | Derived/read-only ordinary availability, or compatibility facade | `max(0, activation_capacity_ap - spent_ap)` before any future explicit grant pool. |

When effective maximum falls, set:

```text
activation_capacity_ap = min(activation_capacity_ap, effective_max_ap)
```

When effective maximum rises or a penalty is removed, do not raise `activation_capacity_ap`. The new capacity becomes available at the next refresh.

This model permits an effective maximum of zero even though the current `max_ap` setter does not.

### 6.2 Why current AP plus clamping is insufficient

Suppose capacity is 3 and the actor spends 1. Current AP is 2. A −1 maximum penalty makes the effective maximum 2.

- `current_ap = min(current_ap, effective_max_ap)` leaves 2 AP and forgets that 1 was already spent.
- `current_ap = effective_max_ap - spent_ap` correctly produces 1 AP.
- if the penalty then disappears, recomputing directly from the restored maximum would produce 2 AP and refund the loss mid-activation.
- the ratcheting activation capacity stays at 2, so availability stays at 1 until refresh.

A spent counter is therefore necessary for the approved reduction rule, but a spent counter **alone** is not sufficient. The activation capacity ceiling is also required to prevent restoration from becoming a grant.

### 6.3 Explicit future AP grants

An explicit grant is not a modifier and should not raise base or effective maximum. When a concrete grant mechanic is approved, represent its unspent amount separately, for example `granted_ap_remaining`, and expose it through a named authoritative method.

One unresolved rule must be approved at that time: whether spending consumes granted AP before ordinary activation AP. The choice affects expiring grants and replay evidence. There is no reason to implement a grant pool in 01.13.1–01.13.3 without an actual granting mechanic, but the state design must avoid treating a grant as negative expenditure.

### 6.4 Worked examples

| Scenario | State transition | Available AP |
| --- | --- | --- |
| Refresh at MIRA baseline | effective 3; capacity 3; spent 0 | 3 |
| Spend 1 | capacity 3; spent 1 | 2 |
| Apply −1 maximum | effective 2; capacity ratchets to 2; spent 1 | 1 |
| Remove penalty same activation | effective 3; capacity remains 2; spent 1 | 1 |
| Next activation refresh | effective 3; capacity 3; spent 0 | 3 |
| Two penalties, −1 and −2 | effective 0; capacity 0; spent unchanged | 0 |
| Remove one penalty | effective 2; capacity remains 0 this activation | 0 |
| Next refresh with remaining −1 | effective 2; capacity 2; spent 0 | 2 |
| Maximum falls below AP already spent | capacity may fall below spent; formula clamps availability | 0 |
| Guard at 2 available | records/spends 2 and ends activation | 0; one reserved reaction remains |
| Terminal at 0 available | cost 0; requires active eligibility and legal adjacency | 0; action may commit once |

### 6.5 Ownership contracts

- **Configuration:** `TacticalArchetype` authors base AP. The reusable unit scene retains a fallback but does not identify species.
- **Runtime:** `UnitStats` calculates effective maximum, activation capacity, expenditure, and available AP.
- **Actions:** `ActionCost` describes cost; `TacticalActionService` validates and commits through `UnitStats` methods.
- **Turn lifecycle:** `TurnManager` calls one refresh method at the existing eligibility boundary and reacts to availability changes. It does not calculate AP.
- **AI:** AI asks shared action queries and reads the same AP snapshot. Exact-value heuristics may choose policy, but never legality.
- **HUD:** HUD displays `current/effective maximum`; optional future detail can explain modifiers. It never changes AP.
- **Replay:** action results record before/after available AP; new feature-gated fingerprints include base, effective maximum, activation capacity, spent AP, and a stable sorted modifier snapshot.
- **Movement:** `UnitStats.speed` remains a separate movement budget consumed only by path queries.

## 7. Risks, dependencies, and decisions

### 7.1 Confirmed issues

1. **Zero effective maximum is unrepresentable.** `UnitStats.max_ap` clamps to at least 1.
2. **Dynamic maximum semantics are absent.** Direct max mutation clamps current AP and loses expenditure history.
3. **Fingerprint coverage is incomplete for future tempo.** Current fingerprints contain current AP only.
4. **Landing-page documentation is stale.** `README.md` says all units begin with 2 AP; current MIRA Resources/tests use 3.

### 7.2 Potential risks

- Guard and Wait bypass `consume_ap()` by assigning zero; leaving this unchanged would bypass spent tracking.
- A zero-capacity active unit can stall if selection progression waits only for an `ap_changed` transition that already occurred before selection. Phase-start selection must skip actors without AP unless a legal zero-AP continuation exists.
- The terminal callback is specific. Adding more voluntary zero-AP actions later could require a shared “has legal zero-AP continuation” query, but 01.13 should not create a generic interaction framework.
- Player portraits equate zero AP with exhaustion even while a free terminal interaction is legal. This is an existing presentation compromise, not a confirmed turn-stall defect.
- AI branches at `current_ap == 1` and loops at `> 0` need explicit 0, 2, 3, and 4 AP tests. They do not demonstrate a current defect.
- Beat damage can remove actors immediately before refresh. Reordering refresh before condition processing would create dead-unit state churn and replay differences.
- Replay feature gating must prevent new fingerprint fields from invalidating old recordings.
- Directly renaming serialized `max_ap` fields can disturb `.tscn`/`.tres` Resources. A compatibility migration or temporary alias is safer.
- `UnitStats.speed` is mutable for carrying and not fingerprinted. This is outside 01.13, but future movement modifiers will need their own replay evidence.

### 7.3 Existing correct behavior to protect

- Three AP materially improves current MIRA rescue tempo and is authored in Resources.
- Rejected/stale actions do not spend AP.
- Guard registers one reaction regardless of AP spent and reactions consume SP, not AP.
- Free objectives remain usable at zero AP when their eligibility path permits it.
- Nested reactions stay in one parent transaction and revision.
- Condition ticks happen once per shared beat, before the next round begins.
- Player, ally, enemy, and replay actions use shared action contracts.
- Movement distance remains independent of AP count.

### 7.4 Decisions requiring approval

1. **Naming migration:** expose `base_ap` as the new Resource property and migrate old `max_ap`, or keep `max_ap` as a deprecated authored alias for one milestone?
2. **Grant consumption:** when a future current-AP grant exists, does spending consume granted AP first or ordinary AP first?
3. **Zero-AP selection presentation:** should a unit with a legal free objective action remain visually “selected/actionable” despite showing `0 / N`, or is the existing terminal affordance sufficient?
4. **Modifier identity:** approve stable `StringName` source IDs with integer values as the narrow representation, or require a small typed AP-modifier value object from the start?

The audit recommends a compatibility alias for naming, deferring grant consumption until a real grant is designed, retaining current zero-AP presentation for the first implementation slice, and using stable source-ID integer modifiers rather than a general attribute system.

## 8. Recommended implementation sequence

The proposed six-slice sequence is sound with one ordering adjustment: current/expenditure lifecycle should land with the effective-maximum calculation because the latter is unsafe without it. Split reviewability by introducing the data surface first, then making dynamic modifiers live together with activation accounting.

### 01.13.1 — Base AP & unit configuration

**Inputs:** approved naming/migration decision.
**Likely files:** `unit_stats.gd`, `tactical_archetype.gd`, archetype Resources, editing guide, archetype tests.
**Acceptance:** Inspector-authored base AP; MIRAs remain 3; a test fixture can use 2 or 4; no class/species name check; no action behavior change.
**Regressions:** archetype lab, match setup, battle smoke, Resource load/import.
**Exclude:** modifiers, grants, movement changes, AI policy changes.

### 01.13.2 — Effective maximum, activation capacity & expenditure

**Inputs:** approved modifier representation.
**Likely files:** `unit_stats.gd`, `action_cost.gd`, `tactical_action_service.gd`, unit tests and action-service tests.
**Acceptance:** derived `max(0, base + modifiers)`; stable source add/remove; capacity ratchets down; spend-all uses a named method; effective zero works; removal grants nothing mid-activation.
**Regressions:** every action cost, Guard/Wait, stale/rejected actions, nested reactions.
**Exclude:** conditions applying AP modifiers, explicit grants, movement modifiers.

### 01.13.3 — Tactical beat and activation refresh lifecycle

**Inputs:** the 01.13.2 state model.
**Likely files:** `turn_manager.gd`, `unit_stats.gd`, battle-controller zero-AP continuation, lifecycle tests.
**Acceptance:** refresh at the existing faction/activation boundary; conditions tick first at beat end; deaths cannot stall; zero-capacity actors are skipped safely; legal free objectives remain possible; no mid-activation restoration.
**Regressions:** turn selection, AI-vs-AI, extraction/rescue/terminal, beat-death recovery, seeds `25005`, `25100`, and previously reported stall seed `726367275`.
**Exclude:** changing 01.12 duration/tick rules.

### 01.13.4 — Conditions & dynamic tempo integration

**Inputs:** one approved condition or fixture that supplies an AP modifier.
**Likely files:** condition definition/component integration, AP modifier calls, focused fixtures.
**Acceptance:** susceptibility/application owns its modifier source; refresh/reapply does not duplicate modifiers; removal/expiry follows the no-refund rule; Leaking and Jammed remain unchanged unless separately approved.
**Regressions:** condition lifecycle, beat timing, Emergency Seal, defeat, replay parity.
**Exclude:** universal modifier framework, movement impairment, injury catalogue.

### 01.13.5 — AI, HUD & replay integration

## 12. 01.13.2 implementation note

`UnitStats` now owns five distinct AP facts: Inspector-authored `base_ap`, derived `effective_max_ap`, the current activation's `activation_capacity_ap`, cumulative `spent_ap`, and derived `current_ap`. Effective maximum is `max(0, base_ap + sum(modifiers))`. Modifiers are integer deltas keyed by non-empty stable `StringName` source IDs. Setting an existing source replaces it; setting zero removes it; unknown removal is a harmless false result. `get_ap_modifier_snapshot()` sorts source IDs so insertion order cannot affect canonical evidence.

At refresh, capacity becomes effective maximum and expenditure resets. During an activation, capacity only ratchets downward to a reduced effective maximum. It never rises until refresh, so removing a penalty or applying a bonus cannot refund or grant an action. Fixed costs call `consume_ap()`. Guard and Wait call `spend_all_remaining_ap()` and therefore preserve their existing result evidence while recording expenditure through the same authority.

The storage-only runtime `max_ap` compatibility property initially read the effective maximum and accepted legacy writes as Base AP configuration. Direct `current_ap` assignment initially remained available for historical fixtures and debug setup. Production action commits no longer assigned either compatibility property directly. `TacticalArchetype` initialized runtime AP through `configure_base_ap(..., true)`.

This slice provides the API only. No equipment, enhancement, or condition applies an AP modifier in ordinary missions. Movement range remains `UnitStats.speed` and is unaffected. Phase scheduling, zero-capacity actor selection, and condition timing remain unchanged for 01.13.3. Replay action before/after AP evidence and historical schemas remain compatible, but fingerprints do not yet include Base AP, activation capacity, expenditure, or modifier sources; feature-gated fingerprint expansion remains explicitly deferred to 01.13.5.

## 13. 01.13.3 implementation note

Faction phases now call `UnitStats.refresh_activation()` once for each living roster member. The method preserves modifiers and status-duration ownership, copies effective maximum into activation capacity, clears expenditure, and refreshes legacy per-turn Defend state. A legitimate zero effective maximum therefore refreshes to zero. `TurnManager` scans explicit activation eligibility at phase start and after each activation, rather than relying on an AP signal that may never fire for a 0-to-0 refresh. Zero-capacity allies and enemies are skipped immediately; an all-zero AI phase passes to the next phase without a timer or policy loop. Manual player phases retain the established End Turn boundary after `player_actions_exhausted`.

Zero AP remains distinct from having no legal action. The battle controller supplies a narrow, read-only objective check for immediately legal Terminal, Rescue, or Extraction actions. This check reads objective and map state while choosing a candidate; the action itself still validates and commits through `TacticalActionService`. AI actors selected under this exception receive one deterministic objective-action opportunity before ordinary AP processing. Completing a free objective action rechecks continuation and advances selection when nothing free remains.

The tactical-beat order remains unchanged: the enemy phase finishes, `tactical_beat_ended(old_round)` synchronously ticks conditions and resolves casualties, battle completion is checked, the round increments, and the new player phase refreshes its surviving roster. Ally and enemy refreshes occur when their own phases begin. Player selection still observes AP signals because manual selection advances after committed presentation. AI controllers retain ownership of ending AI activations; phase-start eligibility removes zero-capacity actors before AI dispatch, avoiding a competing AP callback and preserving replay action ordering.

Runtime `current_ap` is now read-only, and runtime `max_ap` remains a read-only compatibility name for effective maximum. Current fixtures and debug setup migrated to `set_available_ap_for_setup()`, the scene-authored AP fixture migrated to `base_ap`, and lifecycle code uses `refresh_activation_ap()` / `refresh_activation()`. The hidden legacy `TacticalArchetype.max_ap` Resource field remains because it is a deliberate serialized-Resource migration boundary; current authored Resources still prefer `base_ap`.

No replay schema or fingerprint changed in this slice. Current action results and replay order retain their available-AP before/after evidence, but fingerprints still cannot detect divergence in Base AP, capacity, expenditure, or modifier sources. That feature-gated expansion remains assigned to 01.13.5. No condition currently supplies an AP modifier; the first gameplay-visible condition integration remains assigned to 01.13.4.

## 14. 01.13.4 implementation note

`ConditionDefinition.maximum_ap_delta` is the narrow condition-to-tempo contract. It accepts only zero or negative integer values. `ConditionComponent` owns the stable `condition:<condition_id>` modifier source and calls the existing `UnitStats` modifier API when the condition applies or refreshes. One active instance per condition ID and one keyed modifier source mean reapplication refreshes duration without stacking the penalty.

Explicit removal, expiration, component clearing, and defeat cleanup remove the condition-owned source. Removal is idempotent and affects no independent modifier. Because `UnitStats` activation capacity only ratchets downward, cleanup restores effective maximum without raising current capacity or refunding AP; the next legitimate faction-phase refresh adopts the restored maximum. Susceptibility and immunity rejection occur in the action service before component application and create no modifier.

The provisional System Overload Resource is confined to `tests/fixtures/system_overload.tres`: electronic susceptibility, two-beat duration, and -1 effective maximum AP. It is absent from the condition catalog, missions, weapons, hazards, and loadouts. Jammed still only restricts Aim, while Leaking and Bleeding retain periodic HP damage. No replay schema or fingerprint changed; full tempo-state fingerprint evidence remains deferred to 01.13.5.

## 15. 01.13.5 implementation note

The integration audit found one replay gap and one player-UI inconsistency. Replay fingerprints recorded only available AP, so distinct activation capacity, expenditure, and modifier states could compare equal. The Move button also inferred availability directly from displayed AP while the other action buttons consumed authoritative queries. AI already reads `UnitStats.current_ap` and submits through the shared battle-controller and action-service contracts; its last-AP comparisons are tactical choices rather than a second AP calculation.

New recordings opt into `tactical_tempo_enabled`. The gated fingerprint shape records Base AP, effective maximum, activation capacity, spent AP, current AP, and modifier sources sorted by stable ID. Recordings without the flag preserve their historical shape, so neither the replay envelope nor action payload schemas changed. Playback applies the same gate to reconstruction, pre-action comparison, and committed-state verification.

HUD, portrait, and world-bar AP displays continue to observe the single `UnitStats.ap_changed(current, effective_maximum)` signal. Modifier application, removal, expenditure, and legitimate refresh therefore show one consistent authoritative snapshot. The Move button now uses the shared Move query for availability and validation feedback. No presentation component mutates AP state, no AI policy or balance changed, and System Overload remains test-only.
