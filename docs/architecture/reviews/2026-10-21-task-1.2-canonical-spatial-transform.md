# Phase 1, Task 1.2 — Canonical Spatial Transform

## Result

FuseFire now has one documented and regression-protected convention for converting module-local cells, continuous points, directions, connectors, offsets, and visual rotations into placed grid/world space.

The necessary production correction was already present at the start of Task 1.2 in commit `cce128b` (`restore environment geometry contracts`). Task 1.2 preserved that implementation, audited its consumers, strengthened its explicit contract coverage, and produced fresh rendered evidence. No additional production correction was required.

The permanent convention is documented in `docs/generation/spatial-transform-convention.md`.

## Canonical convention

- Grid `+X/-X` maps to Godot world `+X/-X`.
- Grid `+Z` (`DOWN`) maps to world `+Z` (`Vector3.BACK`).
- Grid `-Z` (`UP`) maps to world `-Z` (`Vector3.FORWARD`).
- Rotation 0 leaves local axes unchanged.
- Rotation 1 maps local `+Z` to `-X` and uses Godot yaw `-90°`.
- Rotation 2 maps local `+Z` to `-Z` and uses Godot yaw `-180°`.
- Rotation 3 maps local `+Z` to `+X` and uses Godot yaw `-270°` (equivalent to `+90°`).

The authored module meaning remains the established counter-clockwise grid convention. Only the conversion to Godot's opposite-sign Y yaw changes sign.

`EnvironmentModuleDefinition` owns the shared operations:

- `rotate_cell()` for discrete tactical cells.
- `rotate_point()` for continuous X/Z authoring coordinates using the rectangular module pivot.
- `rotate_direction()` for connector and facing directions.
- `placement_yaw_radians()` for the corresponding Godot presentation yaw.

Module rotation, visual source-axis normalization (`yaw_quarters`), and Asset Lab calibration yaw (`yaw_degrees`) remain separate authoring concepts. The presenter composes them without changing tactical footprints or connector meaning.

## Audited call sites

The following production paths already use the canonical contract and were retained:

- `EnvironmentModuleMapWriter`: tactical effects, elevated surfaces, and vertical links use `rotate_cell()`.
- `EnvironmentModuleLayout`: footprint, clearance, connector, suitability, and visual-envelope transforms use the definition methods.
- `CoherentEnvironmentAssembler`: furniture and obstacle slots use `rotate_cell()`.
- `ModularEnvironmentPresenter._add_visual()`: visual anchor points use `rotate_point()`; module-local offsets and meshes use `placement_yaw_radians()`.
- `ModularEnvironmentPresenter._add_box_visual()`: derived structural centers and box yaw use the same contract.
- Road diagnostic sections use `rotate_point()` and parity-based size exchange.
- The straight-road and curve source corrections remain explicit `yaw_quarters` values rather than calibration changes.
- Road-owned streetlight slot yaws retain the corrected inward-facing values and are verified from their final world-space working faces.

The repository search found no remaining environment-module consumer calculating `placement.rotation * +PI/2`. Rotation code in character locomotion, tactical cameras, and extraction-transport presentation has unrelated semantics and was intentionally left alone.

## Remaining defects and risks

- F4 remains open: calibration records and assembly certification do not yet share a resolved versioned asset contract or invalidation mechanism.
- Task 1.2 does not generalize transforms beyond the supported one-unit horizontal tactical grid.
- Correct module transforms do not prove asset semantic metadata is correct. Working faces and source-axis corrections still require reviewed asset contracts.
- Rendered captures are human evidence, not pixel-golden tests. Transform assertions provide the automated guarantee.
- F1 road normalization and F3 rectangular envelopes currently pass because they were already corrected in `cce128b`; Task 1.2 did not add further road or envelope production changes.

No commit or push was made, following the Task 1.2 constraint.
