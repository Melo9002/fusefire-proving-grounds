# Architecture health and industry comparison

[Architecture index](README.md) · [Source inventory](implementation.md#source-inventory) · [Walkthroughs](walkthroughs.md) · [Ranked performance experiments](performance.md#ranked-experiments)

## A · Strengths to preserve

- **Single tactical authority.** AI and manual input share the query and commit paths. The service validates again before combat RNG or state mutation. Saved replay has a narrow, independently testable boundary via committed requests and fingerprints. This separation also keeps a planning experiment out of replay.
- **Named decisions with different owners.** Objectives define mission intent, commander and difficulty shape preferences, and situational profile resources carry configurable position weights. Tactical branches express requirements such as escort priority without asking players to infer them from a single score.
- **Domain-aware utility.** Directional cover, LOS, physical standing points, expected damage, reaction risk, flanking and spacing are material to the game. They explain much of the calculation. An alternative architecture would still need those inputs and legality checks.
- **Lightweight team coordination.** A per-team context shares bounded temporary claims. The corridor tests show that a locally legal support move can unlock an objective, while a closed recess still prevents a move. Global squad search would add cost without solving a demonstrated need in those cases.
- **Reproducible verification.** A fixed-seed simulator runs normal tactical scenes, real action service tests exercise lifecycle, and F3 surfaces selected choices and authoritative receipts. Replayed actions have their own verification. This is a stronger base for optimization than isolated scorer tests alone.

## Confirmed weaknesses and boundaries

| Severity and scope | Observed source and consequence | Smallest reasonable alternative and risk |
| --- | --- | --- |
| High for responsiveness, narrow correctness risk if untouched | [AIController](../../units/ai_controller.gd) `_carrier_route` and `_move_along_goal_path`, [Pathfinder](../../systems/grid/pathfinder.gd) `_calculate_hypothetical_fallback` and `planning_costs_to_goal`. Route scans, fallback expansion, and goal field can run entirely between yields. The fresh carrier move had a 133 ms uninterrupted rendered slice and a 149 ms process-frame interval. | Prototype a resumable route search with unchanged deterministic ordering and a route-specific validity stamp. Splitting only outer loops can leave one giant search. A different tie break can change candidate value or claimed corridor. Keep both the exact route and authoritative outcome comparison. |
| Medium for changes to tactical policy | [AIController](../../units/ai_controller.gd) `_plan_activation` joins admission, action precedence, repeated eligibility checks, mission handling, routing, follow-up delays, traces and historical low-value counters. Scorers are separately testable, but several decision branches are observable only by exercising a whole activation. Objective role and priority live partly in ObjectiveManager and partly in AIController. The extraction handoff previously proved that bookkeeping changes can cross the authority/presentation boundary. | Preserve the precedence order and named rules. Extract an internal route computation interface if it directly helps slicing. Only separate further policy evaluation from orchestration when behavioral characterization allows it. Changing order can create a new action sequence, consume a lapse roll, or change AP use. |
| Medium for explanation completeness | [BattleController](../../systems/battle_controller.gd) `record_ai_decision`, `_on_action_committed`, and `_report_ai_rejection`. Several action wrappers emit failure diagnostics inconsistently, and some combat decisions publish only after presentation. The two fresh Freight traces drop one terminal Attack explanation each compared with the corresponding old trace. All captured authoritative commits and final states match. | Unify selected proposal and result linkage around the action window where practical. Add terminating-action, scene disposal and intentionally rejected combat controls. A fix should avoid duplicate rows and avoid replacing the replay log with F3's bounded store. |
| Medium for reading historical alternatives | [AIController](../../units/ai_controller.gd) `_build_decision_record` packages the last position and target lists, which are refreshed by different branches, and `_best_reposition_plan` ranks locations locally. In the real traces, the next Attack carries the previous Move candidates. The reposition record contains a post-move origin and decisive plan text with no evaluated-destination list. | Stamp candidate sets with evaluated action/phase and pre-submit context. Retain compact top values and the chosen candidate. This helps precision while keeping historical data copies bounded. Test inspection separately from live overlays. |
| Medium for new caches or background work, current risk bounded by scope | [AIPlanningSnapshot](../../systems/ai/ai_planning_snapshot.gd) captures revision and occupancy for sliced loops. [SquadContext](../../systems/ai/squad_context.gd) has mutable round, claims, corridor and deferred releases. Several caches rely on synchronous lifetime, and the snapshot does not contain a graph, objective, or claims copy. Current code rechecks authority and routes. A long-lived continuation cannot assume the existing check is a complete reusable planning stamp. | Prefer stable value inputs, separate geometry-only from policy validity, and cancel across scope changes. Proven safe local hints can survive an unrelated AP change. Test a changed exit, claimant movement, lost handler and scene teardown while work is suspended. |
| Low to medium, measure before changing | [AIController](../../units/ai_controller.gd) `_find_attack_target` and [BattleController](../../systems/battle_controller.gd) `try_attack` forecast shots; [TacticalActionService](../../systems/actions/runtime/tactical_action_service.gd) `submit_attack` recomputes during admission. Threat evaluation and position scoring can query related lanes repeatedly. End-of-action commit listeners also cost time. The Freight Attack 20 slice was 8.05 ms, much smaller than the carrier hotspot. | Count exact duplicate keys in one decision. Retain final validation and preserve result fields including pre-Aim chance. Match observation shapes before memoization. No evidence yet to justify a global combat cache or moving commit observers off their ordered boundary. |
| Medium, confirmed duplicated work shape | [BattleController](../../systems/battle_controller.gd) `_query_move_data` builds the full reachable/occupiable inventory even for a single destination. It then obtains the exact path/cost and attaches movement poses. A planner can first obtain an inventory and then pay for another in final validation. That validation was 2.37 ms in the studied carrier decision and about 13 ms in one rendered EnemyUnit1 move. That interval includes other validation work, so the redundant part is unquantified. | Measure separating targeted verification from list enumeration and presentation preparation. Preserve error semantics, exact stop/route cost, reaction checks and replay. A targeted query cannot blindly accept the earlier candidate list. |
| Low, bounded diagnostic overhead | [DebugTools](../../ui/debug_tools.gd) stores 80 recent entries and bounds ranked candidate lists at receipt. The controller and battle serialize candidates for publication even when F3 is closed. Step 11 measured publication at about 0.52 ms per event with F3 closed in its sample. The UI bound is not a live heap bound for the producer or simulator. | Measure tracing enabled/disabled with representative move inventories and keep a compact essential decision. Do not infer that suppressing this trace would resolve a 100 ms route search. |

## What other game AI designs offer

These are published practices. The implications for FuseFire are an engineering assessment of its observed implementation.

| Practice | Evidence from industry or research | Implication here |
| --- | --- | --- |
| Utility AI | Mark and Dill describe using scoring curves and weighted alternatives for decisions with more gradations than a hard rule. [GDC Utility Theory slides](https://media.gdcvault.com/gdc10/slides/MarkDill_ImprovingAIUtilityTheory.pdf) | FuseFire already uses score-based target and position selection plus a few comparable plans. Thrash controls and hard gates matter where narrow mission requirements make one score inappropriate. Changing the representation of utility would leave the costly path and LOS queries. |
| Hierarchical decision-making and behavior trees | Isla describes Halo 2's hierarchy and behavior DAG as tools for organizing priority, eligibility and interruption in a larger behavior collection. [Halo 2 GDC proceeding](https://www.gamedeveloper.com/programming/gdc-2005-proceeding-handling-complexity-in-the-i-halo-2-i-ai) | Mission, combat and fallback precedence already form a practical hierarchy. A named internal branch catalog could help if extension cost grows. A behavior tree alone offers no frame deadline for a slow leaf and does not replace deterministic cancellation checks. |
| GOAP | Orkin's F.E.A.R. design plans actions from world-state preconditions and effects, allowing related goals to reuse actions. [Three States and a Plan](https://www.gamedevs.org/uploads/three-states-plan-ai-of-fear.pdf) | More flexible objective chains could later justify a bounded symbolic layer. Step 12 fixtures show the current missions can work with explicit branches and local plans. Treating hypothetical dense combat, resources and occupancy as generic symbolic actions adds model drift and search cost. A future layer should still submit actual actions through the same service. |
| HTN | Guerrilla's Killzone bots and Decima work separate high-level goal/task decomposition from lower-level execution and discuss debugging the decomposition. [Killzone 3 engineering chapter](https://www.gameaipro.com/GameAIPro/GameAIPro_Chapter29_Hierarchical_AI_for_Multiplayer_Bots_in_Killzone_3.pdf) · [Guerrilla's Decima talk](https://www.guerrilla-games.com/read/htn-planning-in-decima) | Explicit task decompositions could become useful with many compound objective types. Current rescue/extraction and terminal chains are small and observable. An HTN migration now would add authoring and replay/trace verification work while still depending on the same occupied graph. |
| Blackboard or shared context | Corkill explains shared problem state as a coordination mechanism for independent contributors. [Blackboard Systems](https://dancorkill.com/pubs/ai-expert.pdf) | The team context is a small shared-memory design, with direct owners, named intentions and expiry. Expanding it into an opportunistic whole-team planner would change ordering and state ownership. Keep shared facts small and independently invalidatable. |
| Hybrid rule and utility | Guerrilla describes procedural tactical position evaluation from static and dynamic world facts. [Killzone dynamic tactical positions](https://www.guerrilla-games.com/read/killzones-ai-dynamic-procedural-tactics) | FuseFire's combination fits close-range tactics. A rule can protect an objective or veto an illegal cell. Utility can compare how well the remaining positions serve it. Keep that distinction explicit in code and diagnostics. |
| Time-sliced work and prepared information | CryEngine documents queued path requests with a frame quota. Incremental search research demonstrates path reuse under changing edges in its own domain. [CryEngine pathfinding](https://www.cryengine.com/docs/static/engines/cryengine-3/categories/1114113/pages/1048581) · [Koenig and Likhachev, D* Lite](https://publications.ri.cmu.edu/d-lite) | Schedule the expensive synchronous work itself in resumable chunks. Prepare stable graph data early where measurements support it. Incremental repair across sparse changes is a later experiment with real invalidation cost. Godot's live SceneTree and shared AStar objects set a boundary for worker-thread proposals. [Godot thread-safety guidance](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html) |

## A–E decision

**A** Preserve authority, seeded randomness, per-unit heuristic choice, short plans, squad expiry and replay. **B** Improve trace provenance and isolate the routing work needed for scheduling. **C** Profile endpoint internals, slice the dominant work, then remove verified duplication or bound it with proofs. **D** Consider immutable snapshots, wider cleanups or threaded searches only if targeted experiments fail to reach the frame budget. **E** Keep strategic multi-turn planning, partial information, mission task authoring and richer joint planning in the capabilities backlog. Those change the game AI's goals and test matrix.

**Recommended first approval:** a bounded #4 experiment on the reproduced Rescue route. Establish an exact baseline, record per-query/expansion cost, and prototype revision-checked continuation scheduling with no changed path choice. Accept it only with rendered frame-time improvement and preserved legal outcomes, route recovery, cancellation, deterministic ordering and replay.
